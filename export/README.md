# Noor Al-Thaqalain — production package

Static production build of the website **مجموعه قرآنی و تربیتی امیرالمؤمنین نورالثقلین**
(React 19 + Vite). Everything the site needs — HTML, CSS, JavaScript, Persian fonts, images and
the scroll-driven hero video — is inside these folders. It runs on ordinary shared hosting
(Apache/cPanel, Nginx) and on WordPress, with **no Node.js, no database and no external service**
on the server.

## What is in the box

```
noor-al-thaqalain-static.zip        → the whole site as static files (any web host)
noor-al-thaqalain-theme.zip         → the same site as a WordPress theme
```

You only need one of them:

| Your situation | Use |
| --- | --- |
| You want the site on your existing WordPress installation | `noor-al-thaqalain-theme.zip` |
| The domain/subdomain is not a WordPress site (its own document root) | `noor-al-thaqalain-static.zip` |

---

## Option A — WordPress theme (recommended for WordPress hosting)

1. Log in to WordPress admin (`/wp-admin`).
2. **Appearance → Themes → Add New → Upload Theme**.
3. Choose `noor-al-thaqalain-theme.zip` → **Install Now** → **Activate**.
4. Open the site. Done — no permalink, rewrite or plugin configuration is required.

Notes:

- The theme contains the built app under `assets/` and loads it with a normal
  `<script type="module">`; PHP is only used by `functions.php` to read the build manifest.
- Navigation uses hash URLs (`/#/quran`, `/#/news/…`), so it works with **any** permalink
  structure and needs no `.htaccess`/`nginx` rewrites.
- It works whether WordPress is installed at the domain root (`example.com`) or in a
  subdirectory (`example.com/blog/`): asset and image URLs are resolved at runtime from the
  theme folder.
- The theme takes over the public front end completely. WordPress pages and posts are not
  displayed by it; the site's own content is compiled into the bundle (see *Updating the site*).
- Deleting the theme from WP admin removes it cleanly; nothing is written outside the theme folder.

## Option B — Static files on any web server

1. Unzip `noor-al-thaqalain-static.zip`.
2. Upload **the contents** of `noor-al-thaqalain-static/` (not the folder itself) into the document
   root of the domain/subdomain — usually `public_html` in cPanel/File Manager or FTP.
3. Make sure hidden files are uploaded: **`.htaccess` is required** — it rewrites clean URLs such
   as `/about` and `/news/…` to `index.html`.
4. Open the site.

Subfolder or Nginx notes:

- Apache, subfolder install (e.g. `example.com/noor/`): open `.htaccess` and set
  `RewriteBase /noor/`. The build itself must be made with a matching base
  (`pnpm exec vite build --base=/noor/`), which happens on a machine with Node.js — not on the host.
  The simpler route on cPanel is to put the site in an **add-on domain or subdomain**, which has
  its own document root; then upload as described above with no changes.
- Nginx:

  ```nginx
  location / {
      try_files $uri $uri/ /index.html;
  }
  ```

- `404.html` is included for hosts that serve it automatically; the `.htaccess` already covers
  every unknown path with the app shell.

## Assets, fonts and the hero video

- **Hero video**: `videos/hero-scrub.mp4` (theme: `assets/videos/hero-scrub.mp4`), ~2.2 MB,
  ~2.2 MB/4 s. It is *not* autoplaying footage — the visitor's scroll sets `video.currentTime`, so
  the clip must be encoded all-intra (every frame a keyframe) to seek smoothly. The committed file
  is exactly that: H.264, `-g 1`, no audio track, `+faststart`. If you replace it, re-encode the
  same way:

  ```bash
  ffmpeg -i input.mp4 -an -c:v libx264 -preset slow -crf 24 -pix_fmt yuv420p \
         -g 1 -sc_threshold 0 -movflags +faststart videos/hero-scrub.mp4
  ```

  The server must send it as `video/mp4` and support byte ranges (Apache and Nginx do by default;
  the bundled `.htaccess` registers the MIME type).
- **Fonts**: Vazirmatn (UI) and Amiri (Qur'anic text) are self-hosted in `fonts/` as `.woff2`.
  No Google Fonts, no CDN.
- **Images**: `images/hero-architecture.jpg` plus inline SVG ornaments generated by the app.
- Nothing on the page requests a third-party domain. The only outbound requests in the whole site
  are for its own files.

## Before you go live: what does *not* work independently

The build has **no Base44 runtime dependency**: no backend, no cloud database, no auth service and
no API calls. Verified in the shipped bundles — they contain no Base44 SDK, URL or environment
value. (The repo's dev-only preview flag `BASE44_PREVIEW_MODE` and the Docker labels are sandbox
tooling and never reach these packages.)

What that means for features that expect a server:

1. **Admin panel (`/#/admin`)** — a client-side content editor. The passphrase gate is cosmetic
   (default: `noor1405`; a different one can be compiled in with the `VITE_ADMIN_PASSWORD` build
   variable). Edits are saved in **that browser's localStorage**, so they are not shared between
   devices and visitors never see them. It is a preview tool, not a multi-user CMS.
2. **Contact form and activity registration** — they validate input and show a confirmation, but
   **no email is sent and nothing is stored on the server**; submissions only land in the visitor's
   own browser. To actually receive messages, connect a form backend (a WordPress form plugin, a
   service such as Formspree, or a small PHP endpoint) — that requires a code change.
3. **Content is compiled in** — text, news, events and gallery items come from the bundle. Changing
   them permanently means editing `src/content/defaults.ts` (or using `/admin` to preview wording)
   and rebuilding; the WordPress admin screens do not edit this site's content.
4. **No search, comments, user accounts, payments or analytics** — none exist in this project, so
   nothing is lost by moving to static hosting.

## Updating the site later

On a development machine with Node.js ≥ 24 and pnpm (never on the web host):

```bash
pnpm install
pnpm export:build          # writes export/…-static and export/…-theme
bash scripts/export-zip.sh # zips both packages
```

Then re-upload the changed package. Built file names are content-hashed, so browsers pick up new
assets automatically; `index.html` is served with a no-cache policy by the bundled `.htaccess`, and
the theme prints the new hashed script name from its manifest.

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| Refreshing `/about` gives a 404 | `.htaccess` was not uploaded (hidden file) or `mod_rewrite` is off. On Nginx use the `try_files` rule above. |
| Blank page | The browser is too old for ES modules, or a JS file was not uploaded completely. Check the browser console / the Network tab. |
| Hero shows a still photograph only | The video did not load: check that `videos/hero-scrub.mp4` was uploaded, is served as `video/mp4`, and opens directly in the browser. Visitors with *reduce motion* enabled intentionally get the photograph instead. |
| Text renders in a fallback font | `fonts/*.woff2` missing or blocked. The bundled `.htaccess` sets the correct MIME type. |
| WordPress says the built files were not found | The `assets/` folder is missing from the uploaded theme; re-upload `noor-al-thaqalain-theme.zip` instead of copying files piecemeal. |
